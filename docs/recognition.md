识别是描述性的：扩展名、完整目录片段和文件名只提供可能用途，不证明真实文件格式、应用归属或可删除性。界面显示“可能是”和匹配依据。不会将识别结果转换为清理规则或删除授权，原有 Windows 位置说明继续保留。

## 格式与维护

JSON 是规则的维护格式，运行时并不逐条遍历 JSON。顶层为 `schema_version`、`revision`、`rules`；当前支持版本 1。编辑器可以关联 [JSON Schema](../rules/recognition.schema.json)，Rust 加载器同时拒绝未知字段、重复 ID、重复匹配条件、空模式和非法路径模式。

- `category`：用途类别；覆盖矩阵按它分组，不参与删除判定。
- `extension`：只匹配文件后缀，支持 `.tar.gz` 等复合后缀，不匹配同名目录。
- `file_name`：匹配完整文件名，例如 `ext4.vhdx`，不把它误当作任意 `.vhdx`。
- `directory_sequence`：匹配连续且完整的目录片段及后代，文件名本身不参与目录匹配。组件末尾可写 `_{version}`，匹配非空 ASCII 数字或点分数字后缀，如 `dingtalk_134`、`dingtalk_8.5.5`，不匹配 `_backup`、`_133-old` 或跨目录内容；`within` 同样支持此形式。
- `drive_root_file`：只匹配盘符根目录的指定文件，不匹配普通目录或 UNC 共享下的同名文件。
- `within`：附加祖先目录条件。主条件必须满足，且主匹配之前至少命中一个列出的完整目录序列。例如 `.cfa` 必须位于 `media cache files` 或 `peak` 下；目录规则 `msg/attach` 必须位于 `xwechat_files` 内，倒序不算。它不读取磁盘内容或检查相邻标记文件。
- `priority`：越小优先级越高，默认 100。系统维护和仓库等需要保留整体用途的位置使用较高优先级。

同优先级依次选择：盘符根文件、组合条件、目录位置、完整文件名、通用扩展名；同类型优先选择版本占位符更少的模式，再选择更长的模式（组合条件计入目录条件长度），最后以规则 ID 排序保证稳定。这样具体版本确有特殊布局时可以覆盖通用规则。重排 JSON 不改变结果。

避免单独使用 Cache、data、target、.bin、.dat、.bak、.sav 等歧义较大的名称。来源仅说明通用用途时，不把推断写成已确认归属。新增条目必须有可追溯来源、处理建议，并通过正反例测试；不能只为提高条目数量而拆分同义规则。

覆盖矩阵由 `scripts/recognition-coverage.mjs` 从 JSON 生成。修改规则后运行 `pnpm recognition:docs`；`pnpm check:recognition` 检查文档是否同步，已接入 `pnpm check`。维护工具只在开发时运行，不进入用户的扫描流程。

## 运行时索引

首次匹配时解析一次内置 JSON，并建立扩展名、完整文件名、盘符根文件名的哈希表及目录组件前缀树。后续查询只探测当前文件名的后缀和路径中的目录序列，附加条件仅对命中的候选规则计算。

不读文件内容，不额外遍历磁盘，也不发送网络请求；解释按当前结果分页生成。0.16轻量分类和完整说明复用同一匹配选择逻辑，内存分析索引只增加规则序号、类别和同规则祖先关系；不保存完整说明，不写入历史数据库。索引让无关规则不再参与每个条目的线性比较。具有大量相同匹配键的规则仍需检查该键下的候选条件，不承诺任意规则集的固定耗时。
