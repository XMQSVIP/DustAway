# CPU 用途模型 v4 验证（2026-10-29）

本轮补强数据库文件的拒绝判断边界，模型 ID 为 `purpose-nb-v4-e8149b38a69a`。模型仍为 14,338 字节、86 个词项、225 条合成训练记录；词权重和先验与 v3 完全相同。真实数据没有进入训练，没有增加依赖或 GPU 要求。

## 依据和改动

复核既有真实元数据时，Local Storage / Session Storage 中同时出现数字 `.log` 和 `LOG` / `LOG.old`。二者不能仅凭“日志”名称归为同类用途：

- [LevelDB 实现说明](https://raw.githubusercontent.com/google/leveldb/main/doc/impl.md)区分保存数据库更新的数字日志、排序表、清单、当前清单指针与诊断信息日志。
- [LevelDB 文件名源码](https://raw.githubusercontent.com/google/leveldb/main/db/filename.cc)提供数字 `.log`、`.ldb`、`.sst`、`.dbtmp`、`CURRENT`、`LOCK`、`MANIFEST-数字` 的命名依据。
- [Chromium DOM Storage 说明](https://chromium.googlesource.com/chromium/src/+/main/content/browser/dom_storage/README.md)说明 Local Storage 和 Session Storage 的应用状态及会话恢复用途。

本机观察到的数据库文件已受持久存储目录保护，没有发现这批路径被 v3 错误提示。由此构造脱离该已知位置的边界路径后，发现 v3 会把 `logs/000003.log` 或 `leveldb/logs/service.log` 等推测为普通日志。这是合成边界问题，不能写成发现了 9 个真实文件误判。

v4 将完整目录名 `leveldb` 纳入敏感位置；上述数据库文件名、格式和纯数字 `.log`（含已支持的数字轮转）只能抑制缓存/日志/临时用途提示。新增 `protected_database_file` 拒绝原因，不增加任何清理权限。`LOG` / `LOG.old` 没有被一概标成数据库数据；位于持久存储目录内时仍按位置保护。真正按日期数字命名的普通日志也可能拒绝，这是本轮有意保留的歧义。

## 来源辅助复核与冻结留出检查

在原来 96 条盲标开发样本中，对 44 条具有对应存储布局、文件名及上游依据的记录给出临时用途标注：40 条应用数据、4 条数据库诊断日志。其余 52 条保持待复核，没有将空标签当作确认未知。

复核人为 Codex，方法明确记为 `source_metadata`，**不是人工确认、正文核查或已安装版本验证**。样本只覆盖单机、同一 Electron/编辑器生态的部分持久存储位置，选择有依据的子集也带来选择偏差。复核没有复制模型结果或将根目录参考标签直接用于全体文件；例如数据库诊断 `LOG` 与数字 `.log` 使用不同用途标签。

完成模型后先保存模型、推理源码与 release 程序的 SHA-256，再对另两个应用抽出的 44 条盲标候选复核：其中 22 条存储记录具有对应依据（19 条应用数据、3 条诊断日志），其余 22 条仍待复核。标签和模型指纹在首次 v4 留出推理前再次锁定；只推理这 22 条，另外 409 条留出记录未由 v4 推理。v2 最初保存过未被分析的留出输出，历史情况见 v3 记录。

观察工具现在要求逐条声明 `human` 或 `source_metadata`，并把方法计数和复核文件指纹写入导出 provenance。评估器不再把所有外部评估集写成“合成集”，而明确说明结果仅相对于提供的标签。新增边界集在 `model:validate` 中要求 15 条保护样本全部拒绝、10 条正常对照全部保持；样本改变会使冻结对比指纹检查失败。

- `cargo test -p dustaway-core --locked`：172 项通过、2 项既有资源基准按配置忽略。

- Core 全目标 Clippy（`-D warnings`）、Rust 格式和相关脚本格式检查通过。
- Release CPU 程序构建成功。当前合成工作负载十万次预测，预热后三轮 441.13、420.54、424.58 ms，中位数 424.58 ms；不含首次加载与磁盘扫描，不作为提速声明。

本轮没有修改前端、IPC 或删除计划，没有重新执行完整桌面回归或制作发布包。人工真值、多机器和普通缓存/日志的独立测试仍未完成。
